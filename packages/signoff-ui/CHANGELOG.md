## 0.13.0

### Minor Changes

- [#237](https://github.com/dgesteves/signoff-ui/pull/237) [`556ab2e`](https://github.com/dgesteves/signoff-ui/commit/556ab2e04029c22546377f153163dd8a42905ab7) - `useAgUiAgent`: answers to interrupts hold up when things go wrong.

  - Each interrupt takes one answer. A second answer before the resumed run started, from a retry, an app's own button or a second card for the same call, started a second `runAgent({ resume })`, even with the opposite decision. The first answer now stands, in `answerAgUiInterrupt` too.
  - If the run that resumes ends before it starts (its request fails, the `runAgent` option rejects, or it is stopped), the answers are taken back and the cards ask again, with a failure in `error`. `respond` and `resolve` no longer reject when that run fails, as `useChat` doesn't, since the approval cards call them without catching.
  - An interrupt past its `expiresAt` takes only a cancellation, as AG-UI requires. Denying it now sends `status: 'cancelled'`. Approving it sends nothing and sets `error` (code `interrupt_expired`); before, the card read Approved, the call kept reading Running, and the client's error went unhandled.
  - `stop()` before the server answers reads as stopped, not as an error saying "This operation was aborted".
  - `parsePartialJson`, which previews a tool call's arguments as they stream, no longer returns nothing for a chunk that ends in an escaped backslash and a `u`, as a Windows path does (`"C:\\Users`): it read that as a cut-off `\u` escape.

  If your app caught the rejection of `respond` or `resolve` to show why a resume failed, read `error` instead (with `status === 'error'`): the promise now resolves either way. `answerAgUiInterrupt` now ignores a second answer to the same interrupt instead of replacing the first.

  `useAgUiAgent` grows by 0.3 kB gzipped (to 3.9 kB).

## 0.9.0

### Minor Changes

- [#154](https://github.com/dgesteves/signoff-ui/pull/154) [`6243cb9`](https://github.com/dgesteves/signoff-ui/commit/6243cb9e1fc5a04488c4e94fc4d77ab9f1bc5cad) - Security fix: a deny rule now holds when a command is written another way. Its pattern also matches each command of a shell line on its own, read from its first word past `NAME=value` settings, a path and a redirect, and past words such as `env`, `sudo`, `sh -c` or `find`'s `-exec`, with a line that ends in `\` joined to the next. So a server rule denying `git push*` now denies `git status && git push`, `/usr/bin/git push`, `GIT_TRACE=1 git push`, `2>/dev/null git push`, `env git push` and `bash -c "git push"`, which a person's rule allowing every command used to approve. The line is split inside quotes too, so a deny rule can also deny a command that only mentions another, such as `git commit -m "wip; git push"`, and after a quote split that way the next word may start a command: that denies `FOO="a;b" git push`, and for `rm*`, `sed -i "s/a;b/c/" rm.txt`. And any word after `sudo`, `timeout`, `env`, `xargs` and the like may start the command, so `git push*` also denies `sudo grep -rn "git push" docs`, and `rm*` denies `timeout 300 npm test -- --grep rm`. Allow rules still match from the first character.

  Deny rules fail closed: one covers an array argument when an item, or the items joined by spaces, match, and covers an object it can't read and a call whose `when` throws. A dotted argument name reads a key of that name as well as the nested argument: an allow rule needs both to match, a deny rule either. In a deny rule's tool pattern, `*` and `?` match any character, so `*` denies every tool, as documented, even one named after an ACP title with a shell operator in it. An allow rule's tool pattern matches as before.

  Matching is bounded for each rule: it gets 20,000 steps, and 30 more for each character it reads, several times what a common pattern takes, so rules such as a dozen secret-scanning `**AKIA**` deny rules still decide a write of several megabytes, and a pattern that takes more stops early. The bound is each rule's, so a call's matching still grows with the number of rules times the length of its arguments. On one plain string, 100 rules of 500 characters that `parseApprovalRules` accepts, built to take the most steps for each character, take about 0.3 s on 20,000 characters (1.3 s before) and 5 s on 400,000 (26 to 27 s before). A deny rule reads a string up to twice, whole and then by command, and an array up to four times: its items, all in one pass, each once however often it comes and counting as one character at least, then the items joined, each read both ways. As deny rules, they take about 10 s on 400,000 characters with a `;` in every 1,000 (26 s before), 20 s on an array of two such strings, and 0.1 s on an array of 40,000 empty strings or of 10,000 different one-character strings, arrays that deny rules used to skip (1 ms). A route that takes rules from a client should cap the length of the tool's arguments, such as with `.max()` on the strings and arrays of its input schema. A rule that stops before it can tell counts against the call: an allow rule allows nothing, and a deny rule denies. `evaluateRules` then reports that deny rule with `unchecked: true`, unless another deny rule covers the call, and `toToolApproval`'s reason says "Denied: the arguments are too long to check against a rule: …" rather than that the rule matched.

  `useApprovalPolicy` no longer erases the saved rules when a rule is added before an async storage loads, or by an effect that waits for `ready`: the change goes over the rules it loads, and is saved with them, in StrictMode too. `answer()` gives a cached outcome only for the call it answered, so another call that comes with the same id is decided from the rules again; it keeps the inputs it answered, not a copy of each. `webStorageRules` leaves out a stored rule with `args: null` instead of throwing on load.

The kit reads the two approval fields AI SDK 7 added (`approval.isAutomatic` for `toolApproval` policy decisions, and `approval.requestReason`) only when they are present, so on AI SDK 6 approvals are always a person's decision and the card falls back to your `description`. Policies, and the "Auto-approved" and "Blocked by policy" labels, remain AI SDK 7 features.
